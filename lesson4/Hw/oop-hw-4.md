# Домашнее задание №4 — Система платежей (ООП, интерфейсы)

## Цель

Научиться самостоятельно проектировать архитектуру классов на основе словесного описания задачи. В отличие от предыдущих ДЗ, здесь нет готовой иерархии — нужно придумать и реализовать её самостоятельно.

---

## Контекст задачи

Представьте систему, в которой существуют разные типы платежей. После подтверждения платежа система должна обрабатывать его единообразно — например, логировать данные и записывать в таблицу трансферов (финансовых операций между пользователями).

Проблема в том, что типов платежей много и в будущем их станет ещё больше. Нужна архитектура, которая позволяет добавлять новые типы платежей **без изменения** уже написанного кода обработки.

---

## Что нужно реализовать

### 1. Базовый класс `Model`

Универсальный базовый класс, не привязанный к конкретной таблице или сущности. Можно оставить пустым.

```php
class Model {}
```

---

### 2. Классы платежей

Два класса, унаследованных от `Model`, описывающих разные типы платежей. Классы **не знают друг о друге**, поля могут называться по-разному (как будто их писали разные программисты).

#### `OnlinePayment`
- Наследуется от `Model`
- Поля (примерные): пользователь, сумма (например, `value`), дата
- Смысл: платёж подтверждается через callback от платёжной системы

#### `CashPayment`
- Наследуется от `Model`
- Поля (примерные): пользователь, сумма (например, `sum`), дата
- Смысл: платёж подтверждается администратором вручную

> **Обратите внимание:** поля в классах могут называться по-разному — это намеренно, чтобы подчеркнуть необходимость интерфейса.

---

### 3. Интерфейс `TransferEmitter`

Интерфейс, который объединяет все возможные типы платежей. Описывает методы, которые **обязан** реализовать любой платёж, чтобы его можно было обработать функцией `processPayment`.

Методы должны возвращать:
- ID платежа
- Сумму платежа
- Пользователя, который провёл платёж

```php
interface TransferEmitter
{
    public function getId(): int;
    public function getAmount(): float;
    public function getUser(): string; // или нужный тип
}
```

Оба класса (`OnlinePayment`, `CashPayment`) должны **имплементировать** этот интерфейс.

---

### 4. Функция `processPayment`

Функция, которая принимает **любой** платёж через тип `TransferEmitter` и обрабатывает его единообразно.

```php
function processPayment(TransferEmitter $payment): void
{
    // Логируем данные через методы интерфейса:
    echo $payment->getId();
    echo $payment->getAmount();
    echo $payment->getUser();
}
```

> Функция **не должна** использовать `instanceof` и **не должна** меняться при добавлении новых типов платежей.

---

### 5. Дополнительные типы платежей (расширение)

Чтобы убедиться, что архитектура работает правильно, добавьте ещё два типа:

#### `CreditPayment`
- Наследуется от `Model`
- Имплементирует `TransferEmitter`
- `processPayment` не должна измениться

#### `TestPayment`
- **Не наследуется** от `Model`
- Имплементирует `TransferEmitter`
- Возвращает заглушки (тестовые данные)
- Также должна работать в `processPayment` без изменений

---

## Итоговый сценарий запуска

В конце скрипт должен несколько раз вызвать `processPayment` с разными типами платежей и вывести результат:

```php
processPayment(new OnlinePayment(...));
processPayment(new CashPayment(...));
processPayment(new CreditPayment(...));
processPayment(new TestPayment());
```

---

## Технические требования

- Использовать **автолоад** (можно взять из материалов урока)
- Неймспейсы **не обязательны** — все классы можно положить в корневую папку
- С базой данных **работать не нужно** — данные можно задавать в конструкторе или хардкодить

---

## Чего нельзя делать

- Использовать `instanceof` в функции `processPayment`
- Делать общий родительский класс для платежей вместо интерфейса
- Менять `processPayment` при добавлении нового типа платежа

---

## Ключевая идея

> Правильная ООП-архитектура позволяет **расширять** систему новыми типами, не изменяя уже написанный код. Интерфейс `TransferEmitter` — это контракт, который гарантирует, что любой платёж умеет отдать нужные данные.
